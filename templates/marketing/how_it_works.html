How it works

From connected account to published post, step by step.

This is the path every piece of content takes through {{ site_name }}, and what the background engine does on your behalf along the way.

1

Create a workspace per brand

An organisation is your agency or company. Inside it, each brand or client gets a workspace with its own channels, calendar, inbox, media library, approval flow, branding and defaults. Invite teammates with a role, and invite clients with the Client role so they only ever see their own workspace.

{% include "marketing/_icon.html" with name="layers" %} Org → workspaces → members{% include "marketing/_icon.html" with name="users" %} Custom roles
2

Connect channels with the platform's own login

Connections use the platform's official OAuth login, a Bluesky app password or a DEV.to API key. Mastodon starts with your instance URL before authorization. Credentials are encrypted in the database and tokens refresh where supported. Review connection warnings before a campaign; a connection can also fail when a post is sent.

{% include "marketing/_icon.html" with name="link" %} {{ networks|length }} networks{% include "marketing/_icon.html" with name="lock" %} Encrypted at rest{% include "marketing/_icon.html" with name="refresh" %} Refresh where supported
3

Capture ideas, then compose

Ideas sit on a Kanban board until they are ready. Promoting one opens the composer with the title, notes and attachments already in place. Select the accounts, write the caption, and adjust anything per platform. The preview on the right shows what each network will render, with its character budget.

{% include "marketing/_icon.html" with name="grid" %} Idea board{% include "marketing/_icon.html" with name="edit" %} Per-platform overrides{% include "marketing/_icon.html" with name="image" %} Media variants
4

Route it for approval

If the workspace requires review, the post moves to pending review instead of the queue. Internal reviewers comment and approve; if client review is on, the client gets a magic link to the portal and does the same, without an account. Reminders go out when a decision is overdue. Every action is recorded.

{% include "marketing/_icon.html" with name="check" %} None / optional / internal / internal + client{% include "marketing/_icon.html" with name="message" %} Threaded comments
5

Schedule into a slot, a queue, or a date

Pick an exact date and time, drop the post into a queue that owns recurring weekly slots per account, or just hit "next available". Recurring rules can repeat a post daily, weekly or monthly. The calendar shows everything, colour-coded by status, alongside custom events like launches.

{% include "marketing/_icon.html" with name="calendar" %} Slots & queues{% include "marketing/_icon.html" with name="clock" %} Workspace time zone
6

Publish and review delivery results

A background worker sends approved due posts and records each account's result. Eligible failures retry with backoff; supported first comments follow after publication. If an outcome is uncertain, delivery pauses for a person to check the actual account and reconcile it before retrying.

{% include "marketing/_icon.html" with name="zap" %} Parallel dispatch{% include "marketing/_icon.html" with name="refresh" %} Retries 1m · 5m · 30m
7

Replies land in the inbox

The conversation types supported by each connected platform sync into the unified inbox through webhooks or polling. Assign conversations, review sentiment and send supported replies through the platform's API. Availability and history vary by platform.

{% include "marketing/_icon.html" with name="inbox" %} Webhooks + polling{% include "marketing/_icon.html" with name="smile" %} Sentiment
8

Measure and repeat

Review the native metrics available for each connected account, such as followers, reach, views, watch time and engagement. Compare reporting periods and use the results to plan the next draft. Metric coverage varies by platform.

{% include "marketing/_icon.html" with name="chart" %} Native insights APIs{% include "marketing/_icon.html" with name="terminal" %} Same data via API
Under the hood

The publishing engine, honestly described.

A single worker process owns publishing. It polls PostgreSQL rather than a message broker, which keeps deployment to two processes and a database.

First-party APIs only

Facebook Graph, Instagram, LinkedIn, TikTok Content Posting, YouTube Data, Pinterest, Threads, Bluesky AT Protocol, Google Business Profile, Mastodon, DEV.to and the X API v2. Your app credentials, your rate limits, your data.

{% include "marketing/_icon.html" with name="inbox" %}

Inbox sync

Meta webhooks deliver supported Page and Instagram conversations. Polling and backfill help sync other supported conversation types; coverage and history depend on the platform.

{% include "marketing/_icon.html" with name="key" %}

Credentials

Platform app keys come from environment variables or, per organisation, from the admin. Account tokens are stored with field-level encryption. Revoking an API key takes effect immediately.

Architecture

Deliberately boring technology

Chosen so a small team can run it for years: a server-rendered Django app, one database, one worker, and no JavaScript build for the application itself.

{% include "marketing/_icon.html" with name="server" %}

Django 5

Server-rendered templates with HTMX and Alpine.js for interactivity. Tailwind for the app's styling.

{% include "marketing/_icon.html" with name="box" %}

PostgreSQL

The database is also the job queue, via a Postgres-backed task runner. No Redis or Celery to operate. SQLite works for local development.

{% include "marketing/_icon.html" with name="image" %}

Media pipeline

Pillow for images, FFmpeg for video. Local disk by default, or any S3-compatible bucket with streamed uploads and downloads.

{% include "marketing/_icon.html" with name="cloud" %}

Deploy anywhere

Gunicorn behind Caddy with automatic HTTPS in Docker Compose, or the included Railway, Render and Heroku configurations.
